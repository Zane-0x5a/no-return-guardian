# 赴死之旅守护器

一个面向《最后生还者 II 重制版》PC 版“赴死之旅”模式的本地战备快照工具。
它在出战前保存兵营里的征途状态，死亡后让你回到这场遭遇之前，而不是丢掉整趟征途。

- **恢复兵营**：回到出战前的兵营，资源、装备和路线照旧，可以重新准备。
- **重开战斗**：回到兵营后按记录自动出发，直接进入同一场遭遇。
- 两个动作都可以在游戏运行时完成，不用退出游戏；也可以完整退出游戏后恢复。

> 非官方工具，与 Naughty Dog、Sony Interactive Entertainment 无关。游戏内恢复会临时挂接游戏进程（见[安全边界](#安全边界)），
> 只用于单人模式，可能不符合游戏的最终用户许可协议，请自行判断、自负风险。使用前建议先备份存档。

## 下载与安装

从 [Releases](../../releases) 下载：

- `NoReturnGuardian-<版本>-setup.exe`：安装程序。默认为当前用户安装到 `%LOCALAPPDATA%\Programs\NoReturnGuardian`，不需要管理员权限；
  安装位置可以改，也可以选择为所有用户安装。升级直接运行新版安装程序，它会先让正在运行的守护器正常退出。
- `NoReturnGuardian-<版本>-win-x64.zip`：便携版，解压到任意位置运行 `NoReturnGuardian.exe`。
- `SHA256SUMS.txt`：两个文件的校验和。

程序没有代码签名，第一次运行时 Windows SmartScreen 可能提示“Windows 已保护你的电脑”，点“更多信息”→“仍要运行”。

需要 64 位 Windows 10/11、.NET Framework 4.8（Windows 10 1903 起自带）和 Microsoft Edge WebView2 运行时（Windows 11 自带）。
游戏内恢复用到的 Python 与 Frida 已随包附带，不需要另装。

### 游戏版本

游戏内恢复依赖对游戏程序的逆向分析，用到的代码地址取自一个验证过的 `tlou-ii.exe`。守护器不限定游戏版本：
每次挂接之前，它核对游戏里所有要挂接、调用和比对的代码是否和验证过的版本逐字节一致。
游戏更新没有动到这些代码时照常工作；动到了就在挂任何钩子之前停下，游戏不受影响，托盘会说明原因。
这时仍可以手动保护战备，并在**完整退出游戏后**恢复；文件恢复按存档格式逐项校验，格式不符时拒绝。
万一恢复已经开始后才出错，守护器会把磁盘上的存档回滚到恢复之前的样子。

### 数据位置与卸载

快照、设置和日志在 `%LOCALAPPDATA%\NoReturnGuardian`（快照库位置可在设置里看到），与程序分开存放。
卸载、升级都不会删除它们；不再需要时手动删除这个文件夹即可。卸载会移除指向这份安装的开机启动项。
程序移动位置后，下次启动时会把已开启的开机启动改到新位置。

### 反馈问题

界面和托盘只说结论：游戏有没有被动过、存档在什么状态、下一步怎么做。出错时的原始原因记在诊断日志里，只保留有限的量：

- `%LOCALAPPDATA%\NoReturnGuardian\guardian.log`：守护器自己的错误记录，满 512 KB 轮换，只留上一份。
- 快照库下的 `native-recovery-logs\`：每次游戏内恢复（`recovery-*`）和出发记录（`departure-*`）的日志，各留最近 20 次。
  同一次恢复的几个文件前缀相同，`.stderr.txt` 是恢复脚本的原始输出。
- `%LOCALAPPDATA%\NoReturnGuardian\state-transcript.tsv`：存档状态的变化，满 2 MB 轮换。

提交 [Issue](../../issues) 时附上出问题那一次的 `recovery-*` 文件和 `guardian.log`。日志里有存档路径，路径中含平台账号 ID，
公开上传前可以把它替换掉。

## 原生恢复：无需重启游戏

1. 打开守护器，出战前在兵营点击“保护当前战备”并确认；
   开着“出发自动保存”时也可以不点，直接从路线板出发（见下文）。
2. 只有两个动作：**恢复兵营**（Ctrl+Alt+F9）和**重开战斗**（Ctrl+Alt+F10）。死亡停在结算页、已经回到赴死之旅菜单、
   甚至还在战斗中（会先放弃本场）都可以直接在游戏里按，守护器自己判断从哪里开始，作用于最近的一份战备。
   也可以在守护器右侧选中一份战备，点它的“恢复兵营”或“重开战斗”并确认；游戏会自动切回前台，面板只留一行进度，成功后自动收起，结果见提示和托盘。
3. 程序在游戏命令层代按“继续”走完结算（不模拟键盘或鼠标），核验菜单和战备后，通过原生载入链恢复。回兵营后核对资源，再次出战。

**重开战斗（实验）**：保护战备后，守护器会记录你从路线板出发的选择（以最近一次为准）。
之后在结算页、菜单或战斗中按 **Ctrl+Alt+F10**：守护器结束本场（战斗中按放弃征途处理），回到这份战备，
再按记录自动出发进入同一遭遇。刚“恢复兵营”回来、还没出发时按，守护器不重新载入，直接从这个兵营出发。
没有出发记录时只回到兵营，你手动出发一次后即可使用；记录成功或失败，托盘都会提示。
站在别的兵营里（比如赢下一场之后，或重启游戏后继续进来的兵营）两个动作都会被拒绝，先在暂停菜单退回赴死之旅菜单再按。
2026-10-01 已在结算页实机重开两次，都进入了记录里的同一遭遇；重开后的资源与交易站尚未单独核对，战斗中重开尚未实机运行。
同日修复：多次重开同一遭遇后，死信投递只显示 `[A] / [B]`。原因是游戏把“已用道具”记在档案里，原生恢复以前不回滚它；现在恢复前会把这类征途统计改回战备时的值（尚未实机验证）。

**出发自动保存（实验）**：设置里的“出发自动保存”默认开启。你在兵营里时，守护器把游戏每次写好的兵营存档暂存一份；
你从路线板出发的那一刻，把出发前的最后一份保存为“出发前战备”，并把这次出发记在它名下，托盘提示“已在出发时保存战备”。
这样每场遭遇都有对应的战备，死亡后按 Ctrl+Alt+F10 就回到这场遭遇的出发前。
它只在实际看到你从路线板出发、并确认那份就是出发前最后写下的兵营存档时保存，走与手动保护相同的全部校验；
没赶上（比如出发前一刻刚拿了东西）时不保存，托盘会说明原因，这时最近的战备仍是上一场的。每个存档只保留最近 10 份出发前战备，手动战备不受影响。
2026-10-01 晚修正：最初的版本存的是游戏处理出发时写下的那份存档。那时游戏已经把征途推进到下一场、把兵营重置给下次来访，
从它回兵营会看到补给箱重新刷满、路线板只剩模板文字。旧版自动保存在清单里显示为“出发后 · 只能重开”：
它们还能重开自己的战斗，但不能回兵营。新版本还没有实机自动保存过。

恢复期间请让游戏保持前台。游戏失焦时会降频，兵营载入可能从约 3 秒拖到 30 秒。
2026-10-01 起结算页按玩家连按的节奏代按，并修复了“分数页内部推进被误判为卡住”的问题。新版本已实机运行两次：结算阶段约 10 秒（主要在等游戏自己存档），全程约 23 秒，旧版中位约 33 秒。

适用范围是手动工作态快照和出发前战备；原生导出重建的 schema 6 快照仍只支持退出游戏后的文件恢复。
恢复调度后失败可能关闭绑定的游戏进程，并尝试回滚操作前的磁盘现场，提示会说明游戏和存档现在的状态；
程序保留自动校验和[诊断日志](#反馈问题)，不伪造玩家验收记录。

## 安全边界

- 不修改游戏程序文件，不模拟键盘或鼠标输入。游戏内恢复用 Frida 在游戏进程里临时挂接少量经过指纹核对的函数，
  完成后撤销并逐字节核对原代码；除了载回玩家自己的战备、把十项征途统计改回战备时的值、重放玩家自己的路线板选择，不改游戏数据。
- 后台监测只读：不覆盖游戏存档，也不按存档变化自动生成战备候选。唯一的自动保存是上面的出发自动保存，
  它以游戏里观察到的路线板出发为依据，可以在设置里关闭。
- 普通文件恢复在游戏运行时仍被硬阻止。制作名单暖恢复的入口关闭。
- 游戏运行且选中可恢复的准备态时，“恢复兵营”“重开战斗”走原生恢复；
  只在死亡后征途已卸载、赴死之旅菜单上下文和独立快照验证成立时执行。
- 每个快照都带 SHA-256 校验；校验失败时拒绝恢复。
- 手动保存必须通过准备态门禁。门禁读取 `gamedata/R0A.save` 的实测状态字：
  已观测的 `00800000` 与 `00800001` 都只作为“状态码已识别”证据，不能单独
  推断画面场景；未知值仍直接拒绝。两种已识别状态还必须同时满足
  R0A/0P 双镜像逐字节一致、写批同代并通过两次稳定探测。近期 R0A
  滚动见证只作为诊断信息，不会要求玩家额外操作来解锁保存。陈旧的
  `SAVEFILER0A` 不会被混入快照；工具会在自己的存储目录内从工作 R0A
  重建完整槽位，写入 CRC32C 与 36 字节尾部，并反向逐字节验证。混代、
  镜像分歧、未知存档头或死亡结算都不会生成快照。
- 若游戏在兵营把四个工作文件全部收起、只留下原生导出的 `SAVEFILER0A`、
  `SAVEFILE0P` 与 `nr.bin`，守护器会走独立的 schema 6 路径：严格验证两个
  槽的 CRC、头部、尾封装、元数据和标识，在守护器目录中逆向还原 R0A/0P
  双镜像，再正向逐字节复现原槽。只缺一部分工作文件、两个槽不同代或任一
  格式未知时仍会拒绝。R0A 只接受已有真实证据的零尾和旧型尾部两种格式；
  `SAVEFILE0P` 只读，恢复时绝不覆盖。
- 恢复前自动保存现场，并支持撤销最近一次恢复。这些恢复前快照默认不在清单里显示，
  “撤销最近恢复”照常可用；要看它们，打开设置里的“显示恢复前快照”。
- 设置里的“自动清理”打开后，每次快照有变化就只留每类（手动、出发前、恢复前）最近 3 份。
  正在用的快照不删：当前保护的、最近一次恢复的、出发记录器正替它记录的，以及撤销要用的那份。
  打开时会先列出要删的份数，确认后才删除。
- 工具按事务一起回滚 `SAVEFILER0A` 与完整 `gamedata` 会话包：兼容槽位先写，
  权威工作态后写，`nr.bin` 最后写。包内包括 `R0A.save`、`R0A.save-backup`、
  `0P.save`、`0P.save-backup` 和 `nr.bin`；
  不会回滚 `savedata/SAVEFILE0P`，也不会覆盖游戏自己的滚动备份。

## 退出游戏后恢复

1. 进入赴死之旅前打开守护器，保持它在托盘运行。
2. 无需退到主界面或退出游戏。在兵营等待存档写批稳定，点击“保护当前战备”
   并确认。工具只读游戏目录，在守护器存储中生成完整恢复槽；若状态未知、
   文件格式未知或尚未稳定，会明确拒绝。
3. 战斗死亡后，先完整退出游戏。只退到主菜单不够：游戏仍会从进程内存
   恢复较新的征途并覆盖磁盘文件。
4. 在工具中选择死亡前的战备，点“恢复兵营”并确认。
5. 工具完成写回与磁盘校验后，重新启动游戏；只有游戏实际进入原战备，才算
   恢复完成。

可在列表中选择任意快照并点击垃圾桶按钮删除；存在未闭合恢复事务时删除会被
阻止。历史自动误捕保留为证据但禁止恢复；新版本不会再产生自动候选。

工作态热导出算法已在两组真实“兵营工作 R0A -> 游戏退出槽”上做到逐字节
完全一致，其战备已完成真实死亡恢复及交易站状态验收。原生导出逆还原已对
真实兵营 `...0654` 现场生成并验证完整八文件战备；第二种 R0A 尾部也由真实
`...09C1` 原始/导出对闭合。
但 schema 6 战备尚未完成一次真实恢复、续玩和交易站验收，因此不把
这一来源的磁盘校验等同于游戏内成功。

历史 T2R 制作人员名单暖恢复转录曾记录目标 `...00D3` 进入兵营后明显更接近
目标而非缓存原代次 `...0177`，并记录了玩家对货币、库存、升级和交易站的检查。
这只是特定构建的实验历史证据；暖恢复当前不属于产品能力，发布入口已禁用，
不能据此承诺可用，也不等同于任意主菜单热写。

## 界面

界面是 WebView2 承载的网页（源码在 `src/NoReturnGuardian.Web`），背景是 Paper Shaders 绘制的流动色场：
守护中是酒红与灰玫瑰，待机沉成夜蓝，征途疑似结束时变成绯红，原生恢复进行中加快流动。左侧是状态、最近保护时间和主操作；
右侧是按天分组的战备清单，选中一行展开它自己的“恢复兵营”“重开战斗”和删除。开关、存档目录、自动清理和面板透明度都在右上角的设置里（滑轨图标）。
图标是一道细线拱门和脚下一扇小门，由 `scripts/make-icons.py` 从同一个色场生成；托盘里小门的颜色就是状态
（香槟色可以保护，石榴红征途疑似结束，灰色其他）。守护器已在运行时再打开一次，会直接把已有的窗口拿出来。
键盘：↑↓ 选择，Enter 恢复兵营（这份不能回兵营时为重开战斗），Delete 删除，Esc 关闭面板。只有暗色界面。窗口关闭只缩到托盘，藏起后页面休眠、色场停止渲染。
开机自启时直接待在托盘里，不弹窗，也不抢你正在用的程序的焦点。
WebView2 运行时无法启动时守护器留在托盘，游戏内快捷键照常可用。

## 从源码构建

需要：

- Visual Studio 2022 或 Build Tools，选“.NET 桌面开发”（MSBuild、Roslyn 和 .NET Framework 4.8）。
- Node.js 20.19 以上（构建界面）。
- Python 3.13（只用于跑测试；发布包自带自己的 Python）。
- Inno Setup 6（只用于生成安装程序）：`winget install JRSoftware.InnoSetup --scope user`。
- 首次构建原生组件时联网：从 python.org 下载 Python 嵌入式包、从 PyPI 下载 Frida，按 `scripts\build-tools.ps1` 里固定的 SHA-256 核对，缓存在 `build-cache\`。

```powershell
.\scripts\build.ps1 -IncludeNativeRecovery   # 构建到 dist\NoReturnGuardian（不加开关则不含游戏内恢复）
.\scripts\test-all.ps1                       # 全部测试：C#、Python、Node 和原生恢复夹具
.\scripts\package.ps1                        # 在全新目录构建、跑全部测试，生成 out\ 下的安装程序、zip 和校验和
.\scripts\test-installer.ps1                 # 安装程序冒烟测试（CI 里跑；会真的启动、退出守护器）
```

界面与 WebView2 组件都编进了 `NoReturnGuardian.exe` 这一个文件；游戏内恢复组件在它旁边的 `native-recovery\`。
检查界面：`.\scripts\render-ui.ps1 -Name 名称` 用本机真实状态截图；开着 `npm run dev` 时加 `-Scene guarding|idle|alert|...` 截模拟场景。
截图模式只读，不执行页面发出的任何命令。

部分测试重放维护者本机的实机记录（`artifacts\`，含个人存档，不在仓库里），没有这些文件时自动跳过；
其余测试都用合成数据，在任何机器上都能跑。`test-all.ps1` 最后列出跳过了哪些、为什么，跳过的不算验证过；
加 `-RequireEvidence` 时有任何跳过都算失败。开发时的辅助程序和 Frida 构建到 `tools\`，与 `artifacts\` 分开。

### 发布新版本

1. 改 `src\NoReturnGuardian.App\Properties\AssemblyInfo.cs` 里的版本号（安装包、zip 和标签都从这里取）。
2. 推送 `v<版本>` 标签。GitHub Actions 会构建、测试、装一遍安装程序（安装、升级、卸载），并建一个附带安装程序、zip 和校验和的草稿发布，确认后手动发布。
